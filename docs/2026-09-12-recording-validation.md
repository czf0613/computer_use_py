# 录制功能自动化验证记录

实现了指定显示器与系统播放声音录制，输出硬件 H.264 / AAC MP4，不采集麦克风。
初始实现默认固定 30 fps，可指定整数帧率和保存路径；未设置码率、质量或数据率限制。
最终接口默认 `video_quality=0.75`，显式 `None` 保留编码器质量策略；仍不设置码率限制。
macOS 源码最低版本为 13.0，官方 wheel 仍保持 macOS 15+ arm64 发行范围。

## 本次验证

环境：本地 macOS 26.6.2 arm64，CPython 3.10.20 与 free-threaded 3.14.6。
所有媒体来自合成 CVPixelBuffer 和 PCM，没有查询或录制真实显示器、系统声音或麦克风。

- Python 3.10：151 项相关测试通过。
- Python 3.14t：150 项通过、1 项按原有条件跳过。跳过的是普通 GIL 环境下的同步 GC
  重入测试；自由线程解释器的 GC 时机不同。测试前后确认 GIL 保持关闭。
- 将离线输入 probe 的部署目标同步为 13.0 后，63 项修饰键生命周期回归通过；
  post/warp 由离线接收器替换，没有向桌面发送输入。
- 两个 ABI 均强制重编译原生测试扩展，并以 `CFLAGS=-Werror` 检查警告。
- 新增原生代码通过 macOS 13.0 / 15.0、生产 / 测试两种配置的 API availability
  编译检查，并通过 Clang 静态分析。
- 在独立临时源码目录执行 `uv build`，成功生成源码包和 Python 3.10 wheel。
  检查新增 Python、类型声明和原生源文件/头文件已打包；wheel 的 Mach-O minos 为 13.0。
  生产版 3.10 / 3.14t 扩展均成功导入，不含 `_test_*` 入口，3.14t 未开启 GIL。

相关测试集：

```sh
SCAPKIT_TESTING=1 CFLAGS='-Werror' uv run --no-sync setup.py build_ext --inplace --force
uv run --no-sync pytest tests/test_recording.py tests/test_recording_integration.py tests/test_native_recording.py tests/test_recording_writer.py tests/test_native_validation.py tests/test_native_arguments.py tests/test_native_capture.py tests/test_capture_lifecycle.py tests/test_async_safety.py tests/test_process.py::test_package_import_does_not_require_the_macos_extension -q
```

合成测试执行真实 VideoToolbox 硬件编码、AAC 编码和 AVAssetReader 解码；本机另外用
ffprobe / ffmpeg 验证容器和解码。覆盖静止画面、固定帧 PTS、短尾帧、静音、音频起点
偏移和截止裁剪，以及并发停止、取消、迟到完成、错误清理和目标文件保护。

独立审查发现并修复了异步停止所有权、截止后音频、文件发布与超时返回之间的竞态，
以及执行器取消排队清理任务后遗漏 stop/abort 的问题，均有对应回归测试。

## 首次实际录制

用户随后明确授权录制正在播放视频的当前主屏幕 20 秒。使用默认 30 fps，
录制主屏幕 ID 5；没有操作视频播放器或更改系统权限。

- 输出：`data/recording-main-20260912-214746.mp4`（本地忽略目录，不纳入版本控制）。
- 图像：3840×2160，H.264 `avc1`，`yuv420p`，BT.709，602 帧。
- 声音：AAC `mp4a`，48 kHz 双声道；平均音量 −17.1 dB，确认存在非静音信号。
- 音视频轨道起点均为 0，容器报告两轨时长均为 20.035042 秒。
- 文件：81,185,374 字节，约 77.4 MiB；按本次内容折算约 231.9 MiB/分钟，
  总平均码率约 32.4 Mbit/s。没有设置编码码率或质量参数。
- ffmpeg 完整解码 602 帧及全部音频成功，无解码错误。

这次验证了真实 ScreenCaptureKit 在该屏幕和内容下的录制及编码路径。
轨道时间一致不等于已确认感知上的音画同步；QuickTime 实际播放、同步、色彩、
静止首尾及其他帧率仍需单独观看或测试。文件大小仅代表本次内容和分辨率。

## 卡顿排查与质量控制

用户反馈约三秒后画面卡顿。检查原文件的 602 帧，PTS 间隔始终约 1/30 秒；但对
480×270 灰度缩略帧计算相邻画面的平均亮度差，采用 0.1/255 阈值排除压缩噪声，
估算画面更新从最初约 29 次/秒降到第 6～9 秒约 3～5 次/秒。不同解码帧的哈希值
可能因有损编码而不同，不能直接把不同哈希计为新画面。此前总帧数和解码成功检查
没有覆盖这个维度。

瓶颈位于每帧提交后的 `VTCompressionSessionCompleteFrames`：它强制同步等待编码
完成，而调用者同时负责 ScreenCaptureKit 回调和帧时钟。编码超过单帧预算后，采集
回调无法及时更新缓存，时钟补帧反复使用旧图像。将同一文件离线解码后送入原 writer，
602 次提交中 274 次超过 33.3 ms，P95 38.85 ms，复现了超过实时预算的同步阻塞。

修复后最多允许两帧在途，配置 `MaxFrameDelayCount=1` 与之匹配，仅在停止时排空
编码器。音频跟随已完成的视频时间补齐静音。回归以信号量阻塞编码输出回调，验证
提交能先返回；旧实现失败，新实现通过。另补充异步最终引用释放、编码器取消时未
返回槽位的回收和原生回调所有权检查。独立复查发现的两项生命周期/延迟配置问题均已修复。

按照用户进一步要求，公开接口采用可选 `video_quality`，不增加固定/平均码率参数。
它设置 `kVTCompressionPropertyKey_Quality`，运行时检查当前硬件编码器支持情况。
本机属性查询和设置成功，范围为 0～1；`None` 保留默认策略。

同一份已录制素材离线重编码，统一 30 fps 和静音音轨，约 20.067 秒：

| 输出 | 质量设置 | 文件字节数 | 十进制 MB |
| --- | --- | ---: | ---: |
| 3840×2160 | 默认 | 76,770,280 | 76.77 |
| 3840×2160 | 0.50 | 10,162,606 | 10.16 |
| 3840×2160 | 0.75 | 28,680,650 | 28.68 |
| 1920×1080 | 0.50 | 4,502,778 | 4.50 |

这些是已编码素材的再次编码，源文件中已有重复画面；只能用于验证质量控制和分辨率
对体积的影响，不能代替新的屏幕采集，也不能预测修复后流畅录制的准确大小或画质。
本次 4K Quality 0.5 / 0.75 离线提交均没有超过 33.3 ms；性能数据只代表这次本机测量。

修复后验证：Python 3.10 164 项通过；3.14t 163 项通过、1 项既有 GC 时机跳过，GIL
保持关闭；macOS 13/15 生产/测试编译、Clang 静态分析通过。生产源码包/wheel 及
两种 ABI 导入通过，无测试入口。尚未重新录制实际屏幕，需要用户准备后再做流畅度验收。

## 修复后实际录制

用户再次授权录制当前主屏幕，使用 30 fps、`video_quality=0.5`，时长约 20 秒。
输出为 `data/recording-main-q50-20260912-221528.mp4`，继续保存在忽略目录。

- 主屏幕 ID 5，3840×2160，H.264 / AAC，602 帧。
- 视频 20.037958 秒，音频 20.037937 秒，均从 0 开始；完整解码成功。
- 14,621,000 字节，约 14.62 MB，总平均码率约 5.84 Mbit/s。
- 音频平均音量 −18.7 dB，包含非静音信号。
- 使用前述相邻缩略帧亮度差方法，首秒检测到 27 次画面变化，随后每秒 28～29 次；
  后半段保持这一水平。最长连续近重复为一个帧间隔，约 33.3 ms，未再检测到先前
  每秒仅 3～5 次更新及连续多个重复帧的现象。

本次验证支持卡顿修复在当前环境和内容下有效。实际画质、感知音画同步和 QuickTime
播放仍由观看确认；前后录制内容不相同，不能把文件大小之比当作严格受控的压缩率比较。

用户验收后指定默认质量为 `0.75`。公开 Python 接口、原生入口和手工录制工具已统一，
显式 `video_quality=None` 仍使用编码器默认策略，版本号和锁文件同步为 `0.1.1`。

- Python 3.10：CI 中不访问桌面的基础测试集共 266 项通过；可选 MCP 测试 21 项通过。
- Python 3.14t：录制及相关原生/异步回归 164 项通过、1 项按既有 GC 时机条件跳过；
  导入和测试后确认 GIL 均关闭。
- 强制重建测试扩展，`-Werror` 编译、13.0/15.0 生产/测试配置检查和静态分析通过。
- `0.1.1` 源码包与本地 13.0 arm64 wheel 的 `twine check --strict` 通过；生产版
  3.10/3.14t 导入均无测试钩子，源码包包含录制相关源码、头文件与类型声明。

上述为发布前本地结果；远端 macOS 15/26 矩阵、官方 15+ arm64 wheel 和 PyPI 上传

## 发布前补齐 MCP 录制

在创建 Release 前补充 `start_recording`、`stop_recording` 和 `recording_status` MCP
工具，默认参数与 Python API 一致。服务持有一段录制及最近结果，用 ID 防止旧停止请求
影响新录制；跨 HTTP 请求/重连保持录制，在取消请求和服务正常关闭时完成收尾。

- Python 3.10 和 3.14t 均通过 32 项 MCP 假设备协议测试，覆盖输入校验、权限、并发
  开始、重复/过期 ID、文件保护、取消清理、退出收尾和 HTTP 断线恢复；3.14t GIL 未开启。
- 独立审查未发现可操作问题，额外核验 AnyIO 取消启动、启动期间退出和重复取消退出。
- 首轮远端 CI 暴露清理计数测试的基线问题：缺少 ffprobe 时，前序跳过测试的 traceback
  保留句柄直到下一次 GC。先进行 GC 并等待既有 owner 释放后再测当前 owner 生命周期，
  保留原来的保活/释放断言。已在本地无 ffprobe 环境复现失败并验证修复。

MCP 验证仅使用假设备，不采集真实屏幕或声音。用户指南与 CI 已同步包含新增工具和测试。
